# 为什么要做 Parsifal Overlay

## 引言

`parsifal-overlay` 的出发点，来自 platform enabling 以及 kernel / OS 升级工作中的一个很实际的问题。

表面上看，这类工作像是一串彼此独立的 bring-up 和 debug 任务；但在真实工程里，它的复杂度更像一个乘法系统：

- 平台数量
- 需要支持的 kernel 版本数量
- 并行维护的 branch / kernel line 数量

随着这些维度增加，总工作量的增长速度往往远快于表面上“问题数量”的增长。

但与此同时，很多故障又并不是完全独特的。它们的症状、证据模式、排查方法，以及可能的故障类别，往往会在不同平台和不同版本之间重复出现。这里就出现了一个机会：如果这些重复的 debug 结构可以被抽取、沉淀并复用，那么其中相当一部分工作就有机会被自动化，或者至少被大幅辅助。

`parsifal-overlay` 想做的，就是这样一个系统。

---

## 最初的洞察

`parsifal-overlay` 最初的想法其实很直接：

> platform enabling 工作在表面细节上可能各不相同，但它的 debug 结构往往是重复的。

一个新平台、一次 kernel 升级，或者某个 branch 上的 regression，表面症状可能不同，但工程师通常都会做相似的事情：

- 收集故障信息
- 从噪声很大的 artifact 里提取有效信号
- 从历史知识中寻找相似模式
- 分析可能的故障成因
- 把结论和下一步行动写下来

这意味着，这类工作可以被拆成明确的阶段，并交给一个“推理 + 工具”的混合系统去执行。

最初的工作流是：

- Observe
- Extract
- Retrieve
- Analysis
- Generate

在这个模型里：

- **Observe** 负责收集原始故障上下文
- **Extract** 负责从日志或 artifact 里提取有效信号
- **Retrieve** 负责从知识库中找相关知识
- **Analysis** 负责提出可能的解释
- **Generate** 负责生成结构化的故障分析报告

这就是后来 `simple-rla` 的起点。

---

## 为什么原始工作流不够

原始工作流是有价值的，但它有一个关键限制。

生成一份报告当然有帮助，但它本质上更多是在证明：模型能够把已有信息重新组织成一份看起来合理的文档。它并不必然意味着模型真的进行了足够强的推理，更不意味着它已经闭环验证了自己的解释是否正确。

换句话说，一个只生成报告的系统，很容易退化成：

- 带知识增强的总结器
- 对已有 artifact 的重新排版
- 生成“看起来合理”的解释，但没有证据闭环

这对于真实 debug 工作来说是不够的。

真实的 platform enabling 和 kernel debug，需要的不只是总结，而是一个能够：

- 提出具体假设
- 判断当前还缺什么证据
- 主动去收集这些证据
- 用新证据重新评估自己的假设
- 在确认、推翻或阻塞时停下来

的系统。

也正是在这里，设计必须从“报告生成”继续往前走。

---

## 向 ReAct 的转向

为了解决这个问题，设计开始向 ReAct 风格演化：

- Reasoning
- Action
- Reasoning

这一步改变了最后一个阶段的意义。

原先的 `Generate` 不应该只是生成一份静态报告，而应该生成可执行的排障工作，包括：

- 故障分析
- `DEVICE_CHECK`
- `CODE_CHECK`

这些 check 不是点缀，而是连接“初始假设”和“证据验证”的桥梁。

理想中的闭环应该是：

1. 基于 case、提取出的信号和知识库做第一次推理
2. 提出一个最可能的故障机制假设
3. 生成具体的排障检查项
4. 通过 tools 去访问设备和代码库，执行这些检查
5. 收集证据
6. 把原始 case 与新证据一起交回模型再次推理
7. 最终要么确认假设、要么修正假设、要么以 blocked / 需要人工介入结束

这是 `parsifal-overlay` 设计上的核心转折：

> 从“生成一份分析报告”  
> 走向“运行一个主动寻找证据的 debug 闭环”

---

## `DEBUG_STEPS` 的真正含义

在这个设计里，`DEBUG_STEPS` 不是一个更漂亮的输出格式而已。

它其实是系统“下一步行动”的第一份结构化表示。

一个有价值的 `DEBUG_STEPS` 至少应该包含三部分：

- 当前的解释，也就是工作假设
- 用来验证或推翻这个假设的设备侧检查项
- 用来验证或推翻这个假设的代码侧检查项

这意味着，`DEBUG_STEPS` 并不是工作流的终点，而是一个更大证据闭环里的中间计划 artifact。

这个区别非常重要。

如果把 `DEBUG_STEPS` 当成最终产物，那系统仍然只是一个报告工具。  
如果把 `DEBUG_STEPS` 当成执行计划，那系统才会变成一个真正的 debug agent。

---

## 核心闭环

从高层看，这个系统的核心闭环应该是：

1. **Case intake**
   - 获取 Jira case 上下文、附件以及初始元数据

2. **Signal extraction**
   - 从日志和 artifact 中提取有意义的 signature 与 observation

3. **Knowledge grounding**
   - 检索相关历史知识、模式、平台事实与参考资料

4. **Hypothesis formation**
   - 形成一个主解释，同时保留较弱的备选解释

5. **Check generation**
   - 围绕当前假设生成 `DEVICE_CHECK` 与 `CODE_CHECK`

6. **Evidence execution**
   - 通过 tools 在设备和代码仓库上执行这些检查

7. **Evidence evaluation**
   - 用返回的证据去对照当前假设

8. **Decision**
   - 确认
   - 修正并继续
   - 以 blocked 结束
   - 升级为人工 review

9. **Summary and distillation**
   - 总结最终理解
   - 在适当情况下为知识库生成一份可复用的 draft

这才是 `parsifal-overlay` 真正的设计中心。

---

## 这个系统的价值在哪里

这个系统的技术价值，不只是“自动化”本身。

它更大的价值在于：它可以把反复出现的 debug 实践，转化成可以复用的结构。

与其把每个 case 都当成一个完全孤立的新问题，不如逐渐复用其中的中间结构，比如：

- failure pattern
- evidence pattern
- diagnostic action
- 平台限定条件
- code-path 关联
- workaround / recovery pattern

如果这个过程做得好，它就能在平台 × 版本 × 分支的组合爆炸中，降低重复劳动的实际成本。

此外，它还可以把原本只存在于工程师经验中的隐性知识，逐渐变成显式对象：

- 结构化检查项
- 证据需求
- 可复用假设
- 知识库草稿

这其实就是一个知识飞轮的起点。

---

## 超越单次 case 的价值

如果这样一个系统建立起来，它的价值就不只是在处理“当前 live issue”。

它还可以反过来处理那些已经解决的问题，把它们沉淀成未来可复用的知识。

这对应着第二层长期价值：

- 总结已经解决的问题
- 抽取结构化的 failure pattern 和 evidence pattern
- 生成新的知识库条目草稿
- 加上平台 / 版本限定条件
- 由人工 review 后合并进正式知识库

这很重要，因为一个真正有价值的 debug 系统，不应该只是“解题器”，还应该是一个能持续改善自己 grounding 材料的系统。

---

## 边界与风险

这个方向的潜力是真实的，但风险也同样真实。

### 1. 证据执行比报告生成难得多
真正困难的地方，往往不在 reasoning 本身，而在证据收集是否可靠：

- 设备连接可能不稳定
- serial 日志可能不完整、很脏
- artifact 质量可能很差
- repo 状态会因为 branch/version 不同而变化
- 平台元信息可能缺失或含糊

一个推理系统的上限，很大程度上取决于它能信任的证据管线下限。

### 2. “听起来合理的计划”不等于“可执行的计划”
模型很容易生成看起来不错的 debug steps，但它们可能：

- 太泛
- 太宽
- 缺少操作落点
- 不能直接执行
- 执行后也不知道如何解释结果

所以 check 最终必须足够结构化，才能真正支持执行与评估。

### 3. ReAct 闭环可能不收敛
如果没有足够强的约束，系统可能只是不断循环，却没有获取到真正有价值的新证据。

所以必须设计：
- 显式上限
- stop condition
- blocked / human-needed 状态
- 继续下一轮的明确理由

### 4. 自动写回知识库可能污染 KB
已解决 case 的提炼很有价值，但不能直接变成不受约束的自动记忆。

知识库写回在早期应该以 draft + human review 为主，而不是直接自动入库。

### 5. 平台 / 版本限定条件是刚需
很多“看起来相似”的故障，在不同平台、kernel 版本、branch 甚至 firmware 状态下，根因可能完全不同。

所以这个领域里的知识系统，必须保留这些限定条件，而不能只保留一个过于抽象的 pattern。

---

## 设计方向

因此，从长期看，`parsifal-overlay` 不应该是一个泛化的聊天 agent，也不应该只是一个生成报告的系统。

它应该是一个**结构化、可调用工具、受知识约束的 debug 系统**，其核心围绕：

- 明确的 hypothesis
- 明确的 checks
- 明确的 evidence
- 明确的 decision state
- 有边界的迭代推理
- 必要时的人类 review

在这个视角里，最重要的系统对象不是报告本身。

真正重要的是这组关系的持续演化：

- 一个 case
- 当前工作假设
- 仍然缺失的证据
- 计划执行的检查项
- 已收集到的证据
- 关于下一步该怎么做的决策

这才是设计中心。

---

## 非目标

至少在现实可落地的范围内，`parsifal-overlay` 并不试图成为：

- 一个无限制自主行动的 agent
- 取代资深 kernel 工程师的系统
- 一个全自动 patch 生成流水线
- 一个假设所有 case 都能脱离人工解决的系统

它的目标更窄，也更务实：

> 降低重复 debug 成本，提高证据质量，加速收敛到正确解释。

---

## 结语

`parsifal-overlay` 的出发点其实很简单：

platform enabling 的工作量会组合爆炸，但 debug 结构本身往往不会。

正是这个落差，提供了一个机会：建立一个能够结合

- workflow orchestration
- knowledge retrieval
- structured reasoning
- tool-driven evidence collection
- iterative hypothesis refinement

的系统。

这个项目从一个偏“报告生成”的 reasoning flow 开始，正在走向一个更有用的目标：

> 一个能够推理、行动、重新评估，并持续帮助沉淀工程知识的证据驱动 debug 系统。
